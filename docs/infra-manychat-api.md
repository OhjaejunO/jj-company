# 인프라 — Manychat API 연동

> **상태: 보류 확정 (2026-08-18 · JJ 승인).** 키를 발급하지 않았고 호출도 하지 않았다.
> 조사는 read-only 로만 했다 — 계정 접속 0, 크레딧 0.

## 결정

**Manychat 공개 API 를 연동하지 않는다.**

## 왜 — 필요했던 둘이 정확히 «안 되는 쪽»에 있다

이 검토를 부른 계기는 두 가지였다.

1. 광고 릴스 캡션이 약속한 `토망치`·`tomangchi` **트리거의 실존 확인**
2. **퍼널이 안 보이는 것** (키워드별 DM 발송수·클릭수)

**둘 다 API 로 안 된다.**

| 안 되는 것 | 근거 |
|---|---|
| 키워드·트리거 **생성·수정·조회** | 엔드포인트가 없다. 커뮤니티 Ideas 에 「Keyword/Trigger API」가 **미해결 기능 요청**으로 열려 있다 |
| 플로우 생성·수정 | `/createFlow` 없음. 같은 기능 요청에 포함 |
| 통계·분석 조회 | 분석 엔드포인트 자체가 없다. 「플로우 통계는 API 로 못 가져온다」가 커뮤니티 답변의 결론 |

**API 가 실제로 하는 일은 셋뿐이다** — 구독자 조회·수정 / 태그·필드 / 발신(`sendContent`·`sendFlow`).
이 중 우리가 A등급으로 쓸 수 있는 것은 **읽기 5종**(`getInfo`·`getTags`·`getBotFields`·`getFlows`·`getGrowthTools`)뿐이다.

### 보류를 고른 세 이유

1. **월 $39(Pro 이상)가 사는 것이 «읽기 5종»뿐이다.** DM 발송 자동화는 정관 §0 C등급이라 애초에 계획에 없다 — 값을 치르고 얻는 것이 스냅샷 읽기에 그친다.
2. 🔴 **API 키에 스코프 개념이 없다.** 「읽기 전용 키」를 만들 수 없어, 리포트용으로 발급한 키가 **DM 발송 권한을 그대로 들고 있다.** 등급 경계를 키가 아니라 **우리 코드가** 지켜야 하는 구조는 정관 §0 이 싫어하는 모양이다.
3. **자동화가 수작업을 만든다.** 유일한 통계 우회로(봇 필드 카운터)조차 **키워드마다 UI 수작업**이 선행돼야 한다.

## 🔁 재검토 조건 (둘 중 하나라도 성립하면 다시 본다)

1. **Manychat 이 통계 API 또는 트리거 API 를 출시한다.**
   확인 위치 — 커뮤니티 Ideas 보드의 해당 요청이 `shipped`/`planned` 로 바뀌는지, 그리고 `api.manychat.com/swagger` 에 `analytics`·`keyword`·`trigger` 계열 경로가 생기는지.
2. **DM 발송 자동화가 실제로 필요해진다.**
   즉 `sendContent`·`sendFlow` 를 쓸 일이 생길 때. **단 그것은 C등급이라 자동 실행이 아니라 «사람이 누르는 버튼»의 뒷단으로만** 쓴다.

**조건이 성립하기 전에는 다시 조사하지 않는다.** 요금제·엔드포인트는 바뀌므로, 재검토 때는 이 문서가 아니라 **공식 문서를 다시 읽는 것부터** 시작한다.

# 부록 — 봇 필드 카운터 시험 설계안

> **상태: 설계만. 착수 전.** 콘솔 설정은 **JJ 가** 한다(§0 C등급 — 계정 설정 변경).
> **다음 발행 편 «1건에만»** 적용한다. 전 편에 깔지 않는다.

## 목적

「퍼널이 안 보인다」를 **API 없이** 최소 비용으로 뚫어 본다.
정확히는 **«이 장치가 실제로 값을 담는가»를 먼저 증명**하는 것이 목적이다 (정관 §0 — 감지 장치를 만들면 그 장치가 값을 담는지 검증한다).

## 구조

    독자 댓글 "<키워드>"
      → [Manychat 키워드 트리거]           (기존)
        → [Set Bot Field] cnt_<키워드> += 1  (신설 · JJ 콘솔)
        → [DM 발송]                          (기존)

    아침 리포트
      → GET /fb/page/getBotFields → cnt_* 읽기   ← ❌ API 보류로 지금은 못 쓴다

## 🔴 이 설계의 정직한 한계 — 읽는 쪽이 없다

**API 를 보류했으므로 `getBotFields` 로 자동 수집할 수 없다.** 그래서 이번 시험의 산출물은
**«리포트 자동 편입»이 아니라 «값이 쌓이는지에 대한 답»**이다. 읽기는 JJ 가 콘솔에서 눈으로 한다.

그래도 할 값어치가 있는 이유:

- **재검토 조건 2가 성립했을 때 바로 쓸 수 있는 상태**가 된다. 카운터는 심은 날부터만 쌓이므로, 필요해진 뒤에 심으면 그 시점부터 또 0 이다.
- **비용이 0 이다.** 필드 1개와 액션 1개다.
- 실패해도 **되돌리는 비용이 액션 1개 삭제**다.

## 설정 (JJ · 콘솔)

| 순서 | 위치 | 할 일 |
|---|---|---|
| 1 | Settings → Fields → **Bot Fields** | `cnt_토망치` 생성 · 타입 **Number** · 초기값 **0** |
| 2 | Automation → Keywords → `토망치` 플로우 | **Set Bot Field** 액션 추가 — `cnt_토망치` = `cnt_토망치` + 1 |
| 3 | 같은 플로우 | 액션 순서를 **DM 발송 «앞»** 에 둔다 |

**3번이 중요하다.** 발송 뒤에 두면 발송이 실패한 건이 카운터에서 빠져, **«도달 실패»와 «트리거 미작동»을 구분할 수 없게 된다.** 앞에 두면 카운터는 «트리거가 걸린 횟수», DM 실물은 «도달한 횟수»가 되어 **두 값의 차이가 곧 발송 실패 수**다.

## 판정 (JJ · 발행 후 24~48시간)

| 관측 | 읽는 법 |
|---|---|
| `cnt_토망치` > 0 | ✅ 트리거가 실제로 걸린다. 체크리스트 7 이 통과였음이 사후 증명된다 |
| `cnt_토망치` == 0 이고 댓글은 있었다 | 🔴 **트리거 미등록 또는 미작동.** 광고 릴스가 우려한 그 상태다 |
| `cnt_토망치` == 0 이고 댓글도 없었다 | ⚪ 판정 불가 — 장치가 아니라 소재의 문제 |

**세 번째 칸이 이 시험의 역검증이다.** 「0 이 나왔다」만으로 «장치가 고장났다»고 읽으면 안 된다 — **입력이 없었을 가능성**을 먼저 배제해야 장치의 값어치가 증명된다.

## 확장하지 않는 조건

이 시험이 성공해도 **키워드 전체로 넓히지 않는다.** 키워드마다 필드 1 + 액션 1 이 수작업으로 늘고,
읽는 쪽이 자동화되지 않는 한 **손이 드는 만큼만 손해**다. 넓히는 것은 **재검토 조건 1(통계 API 출시)** 이후다.
