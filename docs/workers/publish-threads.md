# Threads 발행 워커 — 양식 4 · 양식 2호 · 층: **발행(신설)** · 상태: **설계 초안** (2026-08-28)

> 🔴 **이 문서는 등재이지 구현이 아니다.** 코드 0줄, 자격(API 권한) 미취득, 발행 실적 0건.
> 정관 §0 «발행은 매체별로 가른다»(2026-08-28)가 이 문서를 가리키고, 그 조항은 **«연다 ≠ 지금 발행한다»**
> 를 같이 못박는다. 아래 승인 장치가 서기 전까지 에이전트는 어느 매체로도 발행하지 않는다.
>
> **왜 «발행» 층이 새로 필요한가.** 종전 세 층(감시·제안·해석)은 전부 **산출물이 `reports\` 에서 끝난다** —
> 틀려도 사람이 안 읽으면 그만이다. 발행은 **바깥으로 나가고 되돌림 비용이 0이 아니다.**
> 같은 층에 두면 «제안 워커의 실패 비용 2점»이 이 워커에도 적용돼 채점이 거짓이 된다.
>
> **앞 워커와의 관계.** `distribution-transform.md`(양식 1호)가 **원고를 만들고** 여기서 끝난다
> (그 문서 RULES: «발행 금지(C등급)»). 이 워커는 **그 원고를 받아 올린다.** 두 워커를 합치지 않는다 —
> 만든 쪽과 올리는 쪽이 같으면 «자기가 쓴 것을 자기가 발행»이라 §0 «작성과 검수는 다른 자리» 와 어긋난다.

## 왜 Threads 만인가

| 제약 | 인스타 Content Publishing API | Threads 텍스트 스레드 |
|---|---|---|
| 캐러셀 장수 상한 | 10 (현행 ep35 **11장**) | **해당 없음** — 첨부 0건 |
| 이미지 포맷 | JPEG 강제 → §0 «화소 손실 0» 위반 | **해당 없음** |
| 무음 영상 | 불가 (덱 mp4 오디오 스트림 **0개** 실측) | **해당 없음** |
| 공개 HTTPS URL | 카드마다 필요 → **발행 전 산출물 선공개** | **해당 없음** |
| 남는 장벽 | 위 넷 (둘은 조문 충돌) | **자격뿐** — API 권한 심사 |

실측 근거와 보류 판정은 `docs\infra-backlog.md` **13번**.
**고정 댓글(핀 고정)은 이 워커 밖이다** — 「고정됐는가」를 API 로 되읽을 수 없어 성공 확인이 불가능하고,
그런 동작은 정관 §0 «감지 장치가 값을 담는지 검증한다» 를 만족시킬 수 없다. **사람 자리로 확정.**

---

**JOB** 승인된 편 1건의 Threads 텍스트 스레드 원고를 **체인 순서대로 게시**하고 결과 URL 을 리포트에 남긴다.

**TRIGGER** 사람 호출 아님 · 스케줄 아님 — **승인 파일의 존재**가 트리거다. `publish_approval\<ep>.json` 이
없으면 워커는 뜨지도 않는다. (승인이 채팅 문장이면 «어느 판본을 승인했는지» 를 나중에 증명할 수 없다 —
§0 머지 조건 2 와 같은 뿌리다.)

**INPUTS** (정본/사본 표기)
- `publish_approval\<ep>.json` — **정본**. JJ 서명. 아래 «승인 파일» 절.
- `reports\<날짜>_dist_epNN.md` — **정본 원고**. `distribution-transform` 워커 산출물 · `distcheck` 통과분.
- 정관 §0 «발행은 매체별로 가른다» · §6 금지 사항 — 절 참조만.

## 승인 파일 — `publish_approval\<ep>.json`

**JJ 가 만든다. 에이전트는 읽기만 한다.**

| 필드 | 값 | 왜 |
|---|---|---|
| `ep` | `"ep39"` | 대상 편. 3확인 ③ |
| `body_sha256` | 원고 파일의 **바이트 해시** | 3확인 ①. 승인은 «그 PR 번호»가 아니라 «그 내용»에 대한 것이다 |
| `chain` | 포스트 순서 배열 (`["p1","p2","p3"]`) | 스레드는 **순서가 곧 내용**이다. 뒤집히면 논지가 바뀐다 |
| `signed_by` / `signed_at` | JJ · KST 시각 | 자격 증명 |
| `signature` | 위 필드에 대한 서명 | 위조 판정의 근거 |

- **해시는 원고 파일 전체**다. 포스트 본문만 재면 소스 맵·첨부 표가 바뀌어도 통과한다.
- **`chain` 을 승인 파일에 박는 이유**: 본문 해시만으로는 «같은 문장을 다른 순서로» 올리는 것을 못 잡는다.

## 발행 직전 3확인 — 하나라도 어긋나면 **거부**

| # | 확인 | 실패 시 |
|---|---|---|
| ① | 승인 파일의 `body_sha256` = **지금 발행할 원고 파일**의 해시 | 거부 · `STATUS: FAIL approval-stale` |
| ② | 승인 파일이 **에이전트 손으로 만들어지지 않았을 것** | 거부 · `STATUS: FAIL self-signed` |
| ③ | 승인 파일 `ep` = 발행 대상 편 | 거부 · `STATUS: FAIL ep-mismatch` |

- 🔴 **거부는 «건너뛰고 계속»이 아니라 중단이다.** 발행을 한 포스트라도 시작한 뒤 어긋나면
  **그 자리에서 멈추고 이미 올라간 포스트 URL 을 전부 보고**한다 — 조용히 넘어가면 반쪽 스레드가
  바깥에 남고 아무도 그 사실을 모른다(§0 «조용히 실패하는 코드를 남기지 않는다»).
- ② 를 무엇으로 재는지는 **미결이다.** 후보 — ⓐ 서명 검증(에이전트가 개인키를 못 가짐)
  ⓑ `publish_approval\` 을 에이전트 쓰기 deny 경로로 두고 파일 생성 주체를 감사
  ⓒ 파일이 커밋돼 있고 커밋 author 가 사람일 것. **셋 중 무엇이든 «에이전트가 만들 수 없다»가
  기계로 증명돼야 한다** — 선언만으로는 ② 가 장식이 된다. **JJ 판정 자리.**

**PROCESS**
1. 승인 파일을 읽는다. 없으면 종료(에러 아님 — 트리거가 없는 것이다).
2. **3확인.** 하나라도 어긋나면 거부하고 종료.
3. 원고에서 포스트 본문을 `chain` 순서로 뽑는다.
4. 순서대로 게시. 각 포스트의 응답 URL·id 를 즉시 기록한다 — **다음 포스트를 부르기 전에** 쓴다.
5. `reports\<날짜>_publish_epNN.md` 에 «포스트별 URL · 시각 · 체인 부모 id · 승인 해시» 를 남긴다.
6. `STATUS:` 를 찍는다.

**OUTPUT** `reports\<yyyy-MM-dd>_publish_epNN.md`. 정본 쓰기 없음 —
발행로그 채널 열은 **JJ 가 기입**한다(§0 «고정 댓글·발행로그는 사람 자리»와 같은 선).

**RULES — 금지 자리**
- 🔴 **`publish_approval\` 을 만들거나·고치거나·서명하지 않는다.** 정관 §6 금지 사항.
  이것을 열면 3확인 전체가 «에이전트가 자기에게 내주는 허가»로 무너진다.
- **원고를 고치지 않는다.** 오탈자를 봐도 고치지 않는다 — 고치는 순간 해시가 갈려 ① 이 거부한다.
  그것이 결함이 아니라 **설계**다. 고칠 것이 있으면 사람이 원고를 고치고 **승인을 다시 만든다.**
- 인스타그램 게시·고정 댓글·DM·이메일 — **그대로 금지**(§6).
- 게이트 판정 해석 금지 · 조문 제안 금지 · 정본 직접 쓰기 금지.

**GATE** 발행 전 `distcheck` 통과가 **선행 조건**이고, 이 워커는 그것을 다시 돌리지 않는다
(승인 해시가 그 통과분을 가리킨다). 이 워커 자신의 검사는 위 3확인이다.

**역검증 (조항과 같이 적는다 — §0)** 케이스를 **서로 분리한다.**
① 원고를 **한 바이트** 고친 판 → ① 만 걸릴 것 ② 에이전트가 만든 승인 파일 → ② 만 걸릴 것
③ `ep` 만 다른 승인 파일 → ③ 만 걸릴 것 ④ 정상 승인 → **통과할 것**.
④ 를 빼면 «전부 거부하는 워커»가 정상으로 보인다(`check-repo-guard.ps1` 과 같은 꼴).

**성공지표** 발행 5편 누적 시점에 **«사람이 손댄 발행 0건»**. 측정: 발행 후 편집 이력.
(«발행 성공률»을 쓰지 않는다 — 거부가 정상 동작이라 그 지표는 장치를 끄는 쪽으로 압력을 준다.)

**FAIL CONDITION** 3확인 중 하나라도 어긋남 · 체인 중간에서 API 오류 · 리포트를 못 씀.
**부분 발행은 `STATUS: FAIL partial-chain <올라간 수>/<전체>`** — 정관 §4 «STATUS 는 완수 여부»에 따라
바깥에 반쪽이 남은 것은 완수가 아니다.

**6질문 답**
① 승인 파일·원고 리포트(둘 다 정본) · Threads API. ② 승인 파일은 **JJ 가 유일 작성자**, 리포트는 워커가 유일 작성자 — 충돌 없음. ③ 정관 §0 발행 조항 · §6 · 앞 워커의 `distcheck` 결과. ④ 타 편 원고 · 메모리 · 미승인 초안 — **읽지 않는다**(승인된 편 하나만 본다). ⑤ 원고 교정 → 앞 워커(R6 `distcheck`) / 체인 순서 교정 → 승인 파일 스키마. ⑥ 같은 교정 3회면 앞 워커의 GATE 로 올린다 — **이 워커는 배우지 않는다**(발행기가 학습하면 원고가 조용히 바뀐다).

**하네스 판정** 봇 메모리 = **부채, off.** 편마다 독립이고 판단 근거가 전부 승인 파일에 있다.
기억이 승인과 갈리면 **갈린 쪽이 바깥으로 나간다** — 이 워커에서 기억은 가장 비싼 부채다.

**채점** 반복 1(편당 1회, 주 2~4) · 시간 1(회당 5~30분) · 검증 2(3확인 전수 기계) ·
**실패 비용 0(바깥으로 나가고 되돌림 비용 0 아님)** · 오염 2(정본 읽기 전용) = **6/10**.
🔴 **6점은 «만들어도 된다»의 하한이다** — 실패 비용 0점이 그 이유이고, 3확인은 그 0점을 메우려는 장치다.
장치가 서기 전에 이 워커를 켜면 **채점이 통과한 적이 없는 상태로 발행이 나간다.**

## 열린 항목 (JJ 판정 자리)

1. **3확인 ② 의 판정 방법** — 위 ⓐⓑⓒ 중 무엇인가. 기계로 증명되지 않으면 ② 는 장식이다.
2. **Threads API 자격** — 권한 심사 대상·소요 미조사. 이것이 실제 착수 선행 조건이다.
3. **부분 발행 복구** — 반쪽 스레드를 지울 것인가 이어 붙일 것인가. 지금은 «보고하고 멈춘다»까지만 정해져 있다.
4. **적용 시점** — ep39 부터. ep35~38 은 소급하지 않는다(현행대로 사람이 발행).
