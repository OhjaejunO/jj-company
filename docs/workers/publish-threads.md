## 승인 파일 — `publish_approval\<ep>.json`

### 🔴 초안·서명 2단 (2026-08-28 개정)

종전 문안은 «JJ 가 만든다» 였다. 그런데 승인 파일의 알맹이는 **본문 해시 5건**이라
사람이 손으로 만들 수 있는 값이 아니다 — 만들라고 하면 결국 «대충 맞겠지» 로 흐르거나
에이전트에게 시키게 된다. 그래서 **만드는 일과 승인하는 일을 가른다.**

| 단계 | 누가 | 무엇 | 자리 |
|---|---|---|---|
| ① 초안 | **에이전트** | `py scripts\publish_threads.py --ep <ep> --draft-approval` — 해시 계산은 기계 몫 | `reports\<ep>.approval.json` |
| ② 서명 | **JJ** | 원고 5포스트를 읽고 판정 → `scripts\move-approval.bat` 더블클릭 | `publish_approval\<ep>.json` 으로 **이동** |
| ③ 발행 | 워커 | `publish_approval\` 에 있는 것**만** 승인으로 본다 | — |

- 🔴 **이동이 곧 서명이다.** 따로 서명란을 채우지 않는다. 그 폴더에 파일이 있다는 것 자체가
  «사람이 옮겼다» 는 뜻이고, 그것을 성립시키는 것은 **에이전트가 그 폴더에 쓰지도 못하고
  이동 배치를 실행하지도 못한다**는 사실 하나다.
- 🔴 **초안 생성이 잠금을 우회하지 않는다.** 에이전트가 쓸 수 있는 곳은 `reports\` 뿐이고,
  워커는 `reports\` 를 승인으로 읽지 않는다. **초안은 «승인해 달라는 서류» 이지 승인이 아니다** —
  어느 폴더에 있느냐가 전부다. 초안만 있는 상태로 워커를 돌리면
  «초안은 있다 — 옮겨야 한다» 를 적고 발행 없이 끝난다(실측 확인).
- **초안에는 서명란을 만들지 않는다.** `signature`·`signed_by` 를 비워 두면 사람이
  «채우면 되는 칸» 으로 읽고, 채워 두면 «이미 서명됐다» 로 읽는다. **아예 없는 것이 맞다.**
- `move-approval.bat` 은 같은 `<ep>.json` 이 이미 있으면 **거부한다.** 승인은 한 번 쓰는 것이고,
  갈아치우려면 사람이 옛것을 직접 치운다.

**아래 표는 그 초안·승인 파일의 필드다.**

| 필드 | 값 | 왜 |
|---|---|---|
| `ep` | `"ep39"` | 대상 편. 3확인 ③ |
| `body_sha256` | 원고 파일의 **바이트 해시** | 3확인 ①. 승인은 «그 PR 번호»가 아니라 «그 내용»에 대한 것이다 |
| `posts` | 포스트 **본문마다** `{"seq": 1, "sha256": "…"}` 배열 | 아래 «승인이 거는 대상» |
| `chain` | `posts` 의 `seq` 순서 배열 (`[1,2,3,4,5]`) | 스레드는 **순서가 곧 내용**이다. 뒤집히면 논지가 바뀐다 |
| `drafted_by` / `drafted_at` | 초안을 만든 도구·시각 | 추적용. **자격 증명이 아니다** |
| `manuscript` | 초안이 잰 원고 파일명 | 어느 원고를 잰 해시인지 |

**`signature`·`signed_by` 필드는 없다** — 서명은 필드가 아니라 **폴더**다(위 2단 표).

- **해시는 원고 파일 전체**다. 포스트 본문만 재면 소스 맵·첨부 표가 바뀌어도 통과한다.
- **`chain` 을 승인 파일에 박는 이유**: 본문 해시만으로는 «같은 문장을 다른 순서로» 올리는 것을 못 잡는다.

### 🔴 승인이 거는 대상 — **컨테이너 ID 가 아니라 본문 해시 + 순서** (2026-08-28 실측 반영)

승인 파일이 컨테이너 ID 를 가리키게 설계하고 싶어지지만 **그럴 수 없다.**
아래 «체인은 순차 강제다» 대로 **컨테이너는 직전 포스트가 게시된 뒤에야 만들어진다** —
승인 시점에 존재할 수 있는 컨테이너는 **1번 하나뿐**이고 2~5번은 아직 세상에 없다.

- 그래서 승인은 **본문 5건의 해시와 체인 순서**에 건다. 그것은 승인 시점에 전부 존재한다.
- 워커는 컨테이너를 만들기 **직전마다** 그 포스트 본문의 해시를 승인 파일의 `posts[seq]` 와 대조한다.
  한 번만 대조하고 끝내지 않는다 — 체인이 도는 동안 원고가 바뀌면 **뒷포스트만 조용히 갈린다.**
- 🔴 **컨테이너 ID 는 승인의 대상이 아니라 실행의 부산물**이다. 리포트에는 남기되(추적용)
  승인·검증의 근거로 삼지 않는다.

| ② | 승인 파일이 **`publish_approval\` 에 있고**, 그 폴더에 대한 에이전트 **쓰기와 이동배치 실행이 «이 회차에» 실제로 거부됐을 것** (아래) | 거부 · `STATUS: FAIL self-signed` |

- 🔴 **거부는 «건너뛰고 계속»이 아니라 중단이다.** 발행을 한 포스트라도 시작한 뒤 어긋나면
  **그 자리에서 멈추고 이미 올라간 포스트 URL 을 전부 보고**한다 — 조용히 넘어가면 반쪽 스레드가
  바깥에 남고 아무도 그 사실을 모른다(§0 «조용히 실패하는 코드를 남기지 않는다»).

### ② 의 판정 방법 — **승인 폴더 쓰기 차단 (2026-08-28 · JJ 확정)**

후보 셋(ⓐ 서명 검증 · ⓑ 쓰기 차단 · ⓒ 커밋 author 검사) 중 **ⓑ 로 확정한다.**

- **에이전트 권한에서 `publish_approval\` 쓰기를 뺀다.** 워커의 `--allowed-tools` 는
  `Edit(reports/**)` 만 갖고 **승인 폴더는 어느 규칙에도 들어가지 않는다.** 정관 §2 대로 경로 차단은
  `Edit(경로)` 로 적는다 — `Write(경로)` 는 파일 권한 검사에 걸리지 않는다.
- 🔴 **선언이 아니라 «매 회차 실증»이다.** `scripts\permission_probe.py` 를 vault-health·두 스카우트와
  **같은 방식**으로 이 워커에도 건다 — 워커가 뜨기 전에 `publish_approval\_probe_should_fail.json` 쓰기를
  **실제로 한 번 시도**해 거부되는지 본다. 거부되지 않으면 그 회차는 `STATUS: FAIL probe` 로 **중단**한다.
  판정 근거는 **파일의 존재이지 봇의 말이 아니다.**
- **양방향이다** — 거부만 보면 «전부 거부하는 상태»와 «제대로 거부하는 상태»가 구별되지 않는다.
  프로브는 같은 호출에서 `reports\` 쓰기가 **성공**하는 것까지 본다(정관 §0 역검증 · `check-repo-guard.ps1` 과 같은 꼴).
- 🔴 **축이 셋이다 — 쓰기 거부 · 쓰기 성공 · «이동배치 실행 거부» (2026-08-28 신설).**
  이동이 곧 서명이므로 **그 배치를 실행할 수 있는 자는 자기 승인을 서명할 수 있다.**
  폴더에 못 쓰는 것과 배치를 못 부르는 것은 **다른 문**이다 — 쓰기 축만으로는 안 잡힌다.
  판정은 배치가 남기는 **표식 파일의 부재**다(`--deny-exec` · `--exec-marker`).
  배치의 `--probe` 모드는 표식만 쓰고 **아무것도 옮기지 않으므로**, 게이트가 열려 실제로 실행되는
  바로 그 경우에도 승인이 움직이지 않는다.
- **실측 (2026-08-28)** — 세 축 통과(`PROBE_DENY_FILE_CREATED=no` · `ALLOW=yes` · `EXEC_RAN=no`).
  역검증: 목록에 `Bash` 를 더하자 **배치가 실제로 돌아 표식이 생겼고** 프로브가
  `FAIL exec-open` 을 냈다. 그때도 쓰기 두 축은 그대로였다 — **축 하나만 움직이는 역검증**이다(정관 §0).
- **왜 ⓐ·ⓒ 가 아닌가.** ⓐ 는 개인키 보관처가 새 공격면이고 «에이전트가 키를 못 가진다»를 다시 증명해야 한다 —
  증명해야 할 것이 하나 늘 뿐이다. ⓒ 는 커밋 author 를 에이전트가 지정할 수 있어(`--author`) 기계 증명이 안 된다.
  ⓑ 는 **이미 도는 장치를 그대로 쓰고**, 매 회차 실측이 남는다.
- 🔴 **이것이 «에이전트가 만들 수 없다»를 증명하지는 않는다 — «이 회차에 만들지 못했다»를 증명한다.**
  차이를 적어 둔다(§0 4층 ④). 권한 밖 경로로 우회하는 길(다른 세션·사람 권한 탈취)은 이 장치가 못 잡고,
  그것은 프로브가 아니라 `settings.json` deny 와 세션 격리의 몫이다.

## 🔴 체인은 **순차 강제**다 — 선생성 후 일괄 게시가 불가능하다 (2026-08-28 실측)

`reply_to_id` 는 **컨테이너 생성 단계**에서 받고, 값은 **직전 포스트의 media id** 여야 한다.
그 id 는 **게시해야만 나온다.** 그래서 컨테이너 5개를 미리 만들어 두고 한꺼번에 올리는 길이 없다.

    [1] 컨테이너 생성 → status FINISHED 대기 → publish → media id 회수
    [2] 그 id 를 reply_to_id 로 컨테이너 생성 → FINISHED 대기 → publish → id 회수
    [3] … 5번까지 같은 묶음을 되풀이

- **실측 근거**: 없는 id 를 `reply_to_id` 로 주면 `Param reply_to_id is not a valid threads_media ID`
  (HTTP 500 · code 100). 즉 **실재하는 게시물 id 여야** 컨테이너가 만들어진다.
- 🔴 **이것이 «부분 발행은 보고하고 멈춘다» 의 기계적 근거다.** 중간에서 끊기면
  **다음 컨테이너를 만들 근거 id 자체가 없다.** 이어 붙이려면 사람이 어디까지 갔는지 확인하고
  새 승인을 만들어야 한다 — 워커가 판단해서 이어 갈 수 있는 자리가 아니다.
- **되돌림 비용도 여기서 갈린다** — n번째에서 끊기면 1~n번은 이미 바깥에 있다.

0. (선행, 사람 요청 시) `--draft-approval` 로 `reports\<ep>.approval.json` **초안**을 만든다.
   초안은 승인이 아니다 — JJ 가 `move-approval.bat` 으로 옮겨야 아래 1번의 트리거가 생긴다.
1. 승인 파일을 **`publish_approval\` 에서만** 읽는다. 없으면 종료(에러 아님 — 트리거가 없는 것이다).
   초안이 `reports\` 에 있으면 «초안은 있다, 옮겨야 한다» 를 적고 발행 없이 끝낸다.
2. **3확인.** 하나라도 어긋나면 거부하고 종료.
3. 원고에서 포스트 본문을 `chain` 순서로 뽑는다.
4. **`seq` 마다 아래 네 걸음을 한 묶음으로** 돈다. 앞 묶음이 끝나기 전에 다음 묶음을 시작하지 않는다.
   1. 본문 해시를 승인 파일의 `posts[seq]` 와 **그 자리에서** 대조한다. 어긋나면 중단.
   2. 컨테이너 생성 — `POST /v1.0/<user_id>/threads` · `media_type=TEXT` · `text`
      (2번부터는 `reply_to_id` = **직전 묶음이 회수한 media id**).
   3. **`status` 가 `FINISHED` 가 될 때까지 기다린다** — 아래 «status 대기».
   4. publish → 응답의 media id 를 **즉시 리포트에 쓴다.** 다음 묶음을 시작하기 **전에** 쓴다.
5. `reports\<날짜>_publish_epNN.md` 에 «포스트별 URL · 시각 · 체인 부모 id · 컨테이너 id · 승인 해시» 를 남긴다.
6. `STATUS:` 를 찍는다.

### status 대기 — `IN_PROGRESS` 에서 publish 를 부르면 실패한다 (2026-08-28 실측)

컨테이너를 만들면 `status` 가 **`IN_PROGRESS`** 로 시작해 잠시 뒤 **`FINISHED`** 가 된다.
준비되기 전에 publish 를 부르면 그 포스트가 실패하고, **체인은 그 자리에서 끊긴다.**

- 조회: `GET /v1.0/<container_id>?fields=status,error_message`.
  컨테이너 객체가 내주는 필드는 **`id`·`status`·`error_message` 셋뿐**이다
  (`media_type`·`text`·`created_time`·`timestamp` 는 전부 `nonexisting field` 로 거절된다 — 실측).
- 🔴 **무한 대기 금지.** 대기에는 **상한(횟수·총 시간)** 을 둔다. 상한을 넘으면 **publish 를 부르지 않고
  보고하고 멈춘다** — `STATUS: FAIL container-timeout <seq>/<N>`.
  상한이 없으면 워커가 조용히 매달려 «도는 중»과 «죽은 것»이 구별되지 않는다(정관 §0).
- `error_message` 가 채워져 오면 그것을 그대로 리포트에 옮긴다. 재시도로 덮지 않는다.
- ⚠️ **대기 시간의 «정상값»은 아직 모른다** — 조사 회차에 둘 다 몇 초 안에 `FINISHED` 가 됐을 뿐,
  표본이 2건이다. 상한은 처음엔 넉넉히 두고 **실제 회차 로그로 조인다.**

**OUTPUT** `reports\<yyyy-MM-dd>_publish_epNN.md`. 정본 쓰기 없음 —
발행로그 채널 열은 **JJ 가 기입**한다(§0 «고정 댓글·발행로그는 사람 자리»와 같은 선).

**RULES — 금지 자리**
- 🔴 **`publish_approval\` 을 만들거나·고치거나·서명하지 않는다.** 정관 §6 금지 사항.
  이것을 열면 3확인 전체가 «에이전트가 자기에게 내주는 허가»로 무너진다.
- **원고를 고치지 않는다.** 오탈자를 봐도 고치지 않는다 — 고치는 순간 해시가 갈려 ① 이 거부한다.
  그것이 결함이 아니라 **설계**다. 고칠 것이 있으면 사람이 원고를 고치고 **승인을 다시 만든다.**
- 인스타그램 게시·고정 댓글·DM·이메일 — **그대로 금지**(§6).
- 게이트 판정 해석 금지 · 조문 제안 금지 · 정본 직접 쓰기 금지.
- 🔴 **원고가 첨부를 선언했는데 실을 수 없으면 발행하지 않는다** (2026-08-30 신설 ·
  백로그 20번 ①). `STATUS: FAIL attachment-unsupported` 로 **승인 대조보다 앞, 네트워크
  호출보다 앞**에서 멈춘다. 이유는 두 겹이다 — ⓐ 첨부 없이 올리면 본문의 «영상 출처:» 류
  라벨이 **없는 것을 가리킨다**(ep39 실사고) ⓑ 「못 붙인다」를 거부로 만들지 않으면
  **조용한 누락**이 되고, 조용한 누락은 감사에도 안 올라온다.
  🔴 **지원 여부를 깃발로 두지 않는다.** `media_support_state()` 가 **소스를 `ast` 로 읽어**
  컨테이너 파라미터의 `media_type` 이 리터럴 `TEXT` 뿐인지 본다 — 구현이 붙으면 게이트가
  **저절로 열린다.** 사람이 깃발을 내리는 걸음이 있으면 그 걸음이 언젠가 빠진다(§0 4층 ①).
  판정 불가(`None`)는 통과가 아니다 — **모르면 멈춘다.**

**다음 발행 회차에 확인할 것 (2026-08-30 · ep39 첫 실전 실측에서 남은 것)**
- 🔴 **쿼터 갈림이 재현되는가.** ep39 는 **루트 1 + 답글 4** 인데(API 실물 조회: P1 만
  `replied_to` 없음, P2~P5 는 각각 직전이 부모이고 `root_post` 가 전부 P1) 쿼터는
  **게시 2 / 답글 3** 으로 갈렸다(합 5는 맞다). 두 번 재서 값이 안 움직였으므로 «정산 중»
  은 아니다. **왜 하나가 «게시» 로 세는지 지금 자료로는 못 가른다 — 확인 불가로 둔다.**
  다음 회차에 발행 전·후 값을 같이 적어 재현 여부를 본다. (상한 250·1000 이라 실용 영향은 없다.)
- 🔴 **`WAIT_TIMEOUT_S = 180` 이 영상에 충분한지는 미검증이다.** ep39 실측 FINISHED 대기는
  **4·3·1·0·3초**인데 **전부 TEXT 컨테이너 값**이다(5건 다 `media_type = TEXT_POST`).
  트랜스코딩이 붙으면 자릿수가 달라진다 — **이 값을 영상에 이월하지 않는다.**
- **게시 시각은 영수증으로 재라.** 라이브 `timestamp` 는 **컨테이너 생성 시각**과 같았다
  (claim 시각과 일치). «언제 나갔나» 는 `post.receipt` 가 정본이다.
  ep39 실측 간격: 게시 9·9·9·12초 · 묶음당 claim→receipt 3·6·5·5·7초 · 5포스트 총 54초.

**GATE** 발행 전 `distcheck` 통과가 **선행 조건**이고, 이 워커는 그것을 다시 돌리지 않는다
(승인 해시가 그 통과분을 가리킨다). 이 워커 자신의 검사는 위 3확인이다.

**역검증 (조항과 같이 적는다 — §0)** 케이스를 **서로 분리한다.**
① 원고를 **한 바이트** 고친 판 → ① 만 걸릴 것 ② 에이전트가 만든 승인 파일 → ② 만 걸릴 것
③ `ep` 만 다른 승인 파일 → ③ 만 걸릴 것 ④ 정상 승인 → **통과할 것**.
④ 를 빼면 «전부 거부하는 워커»가 정상으로 보인다(`check-repo-guard.ps1` 과 같은 꼴).

**성공지표** 발행 5편 누적 시점에 **«사람이 손댄 발행 0건»**. 측정: 발행 후 편집 이력.
(«발행 성공률»을 쓰지 않는다 — 거부가 정상 동작이라 그 지표는 장치를 끄는 쪽으로 압력을 준다.)

**FAIL CONDITION** 3확인 중 하나라도 어긋남 · 체인 중간에서 API 오류 · 리포트를 못 씀.
**부분 발행은 `STATUS: FAIL partial-chain <올라간 수>/<전체>`** — 정관 §4 «STATUS 는 완수 여부»에 따라
바깥에 반쪽이 남은 것은 완수가 아니다.

### 부분 발행 복구 — **보고하고 멈춘다 (2026-08-28 · JJ 확정)**

- **워커가 하는 것은 둘뿐이다** — ① 그 자리에서 멈춘다 ② 올라간 포스트의 URL·id·순번을 전부 리포트에 남기고
  `STATUS: FAIL partial-chain n/N` 을 찍는다. **거기까지다.**
- 🔴 **자동 이어붙임 금지.** 남은 포스트를 이어서 올리지 않는다 — 중단 원인이 «API 일시 오류»인지
  «원고가 갈렸는지»인지 워커는 모르고, 모르는 채로 이어 붙이면 **바깥에 어긋난 스레드가 완성된다.**
  반쪽이 남아 눈에 띄는 편이 조용히 완성되는 것보다 낫다.
- 🔴 **자동 삭제 금지.** 이미 올라간 포스트를 지우지 않는다. 삭제는 되돌림 비용이 0이 아니고
  (읽은 사람·인용·알림은 되돌아오지 않는다) **에이전트가 바깥 상태를 지우는 동작 자체가 §6 자리**다.
- **이어 올릴지 지울지 그대로 둘지는 사람이 정한다.** 워커는 그 판단에 필요한 것(어디까지 갔는가·
  무엇이 남았는가·승인 해시)을 리포트에 다 적어 두는 것으로 제 몫을 다한다.
- **재실행은 새 승인 파일을 요구한다** — 중단된 편을 다시 돌리려면 JJ 가 승인을 다시 만든다.
  옛 승인으로 재실행하면 «어디까지 승인된 것인가»가 흐려진다(3확인 ① 과 같은 뿌리).

### 재기동 조정 — **영수증을 남기고, 켤 때 먼저 읽는다 (2026-08-29 신설)**

위 조항은 «자동으로 이어 붙이지 않는다» 를 정했다. 그런데 **이어 붙이지 않으려면 어디까지
갔는지 알아야 하는데, 그것을 아는 장치가 없었다.** 첫 구현은 `done` 을 메모리 목록으로만
들고 있었고 파일 쓰기는 회차 맨 끝 리포트 한 번뿐이었다 — 3번까지 나가고 죽으면 그 사실이
**아무 데도 남지 않았고**, 다시 켜면 `chain[0]` 부터 `parent=None` 으로 시작해 **1번을 다시
올리고 새 스레드를 하나 더 만들었다.** 조항은 있는데 지킬 근거가 없던 자리다.

- **2단계로 남긴다.** 발행 **직전**에 선점(`post.claim`), 발행 **직후**에 영수증(`post.receipt`).
  자리는 `logs\publish-receipts\<ep>.jsonl` 이고 한 줄이 한 사건이다.
  🔴 **한 줄로 하면 안 된다** — 발행 전에만 적으면 «적었는데 안 나간» 경우를, 발행 후에만 적으면
  «나갔는데 못 적은» 경우를 구별할 수 없다. 두 줄이면 그 사이에서 죽어도 **«나갔는지 모른다»는
  상태로 정확히 남는다.**
- **켤 때 영수증부터 읽는다.** 영수증이 있는 seq 는 건너뛰고, 마지막 영수증의 media id 가
  이어가는 첫 포스트의 `reply_to_id` 가 된다.
- **선점만 있고 영수증이 없는 seq 는 실물로 가른다.** 계정의 최근 포스트를 조회해 본문 해시로 맞춘다.
  - 실물에 **있으면** → 나간 것이다. 그 media id 를 이어받는다.
  - 실물에 **없고** 조회 창이 그 시각을 덮으면 → 안 나간 것이다. 거기부터 올린다.
  - **덮는지 알 수 없거나 조회가 실패하면 → 멈춘다.** `STATUS: FAIL reconcile-unverifiable`.
    🔴 **자동 재시도 금지** — 나갔는지 모르는 것을 다시 올리는 것이 이 장치가 막으려는 사고다.
- **깨진 줄은 조용히 버리지 않는다.** 버리면 «영수증이 없다»(재개)와 «못 읽었다»(중단)가 같아 보이는데
  판정이 정반대다. `STATUS: FAIL receipt-corrupt`.
- 🔴 **`fsync` 는 시험으로 못 잡는다 (§0 4층 ④).** 정상 종료하면 `close()` 가 어차피 flush 하므로
  같은 프로세스 안에서 그 줄의 유무가 보이지 않는다. 값을 하는 자리는 정전·강제 종료뿐이고
  그 상황은 시험으로 만들 수 없다. **변조 시험에서 실제로 안 걸렸다** — 그래서 여기 적는다.

### 신선도 — 승인 이후 **바깥**이 바뀌었는가 (2026-08-29 신설)

3확인의 해시 대조는 «원고가 바뀌었는가»를 본다. 그것은 **우리 쪽 변조만** 잡는다.
승인을 받아 둔 사이에 사람이 손으로 올렸거나, 영수증 없는 회차가 이미 돌았으면 그 상태는 못 본다.

- **발행 직전에 계정의 최근 포스트를 조회**하고, 이제 올릴 포스트의 본문 해시가 거기 있으면
  `STATUS: FAIL duplicate-live` 로 멈춘다.
- **재기동 조정 뒤에 본다.** 순서를 뒤집으면 정상적인 이어가기(1~3이 이미 살아 있는 상태)가
  전부 중복으로 걸린다 — 조정이 «이미 나갔다» 로 판정한 seq 는 검사 대상에서 빠진다.
- **조회 실패는 «중복 없음»이 아니다.** 실제 게시 회차에서는 조회를 못 하면 멈춘다
  (`STATUS: FAIL live-unreadable`). 드라이런은 발행이 없으므로 넘어간다.

### 시작 이벤트 — **3확인보다 앞에 적는다 (2026-08-29 신설)**

종전에는 첫 파일 쓰기가 회차 맨 끝 리포트였다. 승인 확인 도중이나 체인 도중에 죽으면
**아무것도 남지 않아** 바깥에서 «돌았는지»조차 알 수 없었다.

- `run.started` 를 **승인 파일을 읽기도 전에** 적는다. 무엇이 실패하든 «켜졌다»는 남는다.
- 같은 사실을 `logs\publish-threads.started` 스탬프로도 남긴다 — `run_audit.py` 가 읽는 꼴이다.
  정상 종료에서만 지우므로, **남아 있는데 pid 가 죽어 있으면 무기록 종료**다.
  `run_audit.TASKS` 에 `publish-threads` 를 넣어 그 스탬프가 실제로 읽히게 했다.
- 🔴 **로그 파일 쪽은 아직 안 보인다 (§0 4층 ④).** 래퍼는 `publish-threads_<ep>_<날짜>.log` 로
  쓰는데 `run_audit` 은 `<작업>_<날짜>.log` 를 찾는다 — 편별로 나누려고 그렇게 지은 이름이라
  **감사가 그 로그를 열지 못한다.** 지금 무기록 종료를 잡는 것은 **스탬프 한 겹뿐**이다.
  파일명을 맞출지 감사 쪽을 넓힐지는 JJ 판정.
