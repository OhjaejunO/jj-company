## 1. 교정 라우팅 표 — 교정이 생기면 «어디에 적는가»

세션 중 생기는 교정(사실 정정·결정·선호·기법·절차·위험·교훈)은 성격이 다르고 **정본 자리도 다르다.** 자리를 잘못 잡으면 두 가지가 난다 — ⓐ 메모리에만 남아 다음 세션이 못 본다(8/25 pending 25건) ⓑ 정관에 기법이 들어가 500줄 상한을 먹는다.

|---|---|---|---|---|---|

**판별 순서** — R1 → R6 → R4/R5 → R3 → R7 → R2. 사실이면 값부터 고치고, 위험이면 장치부터, 그 다음에야 문서다. 같은 교정이 두 자리에 걸리면 **구현 자리(R6·R5)가 정본**이고 문서(R3·R4·R7)는 참조만 둔다(정관 §0 «실물이 정본»).

**등재 전 기존 조문 대조 — 필수.** 8/25 재고에서 33건 중 **4건이 이미 등재돼 있었다**(크롭 폴백·씬 프롬프트 v3.49, 캐러셀 상한 v3.25.1, 재등록 절차 #71) — 그중 하나는 «조항이 있는데 못 읽어서» 사고까지 냈다(ep29 60초 상한). 등재 전에 `grep` 으로 정본을 먼저 뒤진다: SKILL 은 판본 헤더·해당 절, 정관은 §0~§6, 게이트는 `epcheck.py` 독스트링 목록.

**세션 종료 절차에 «분류 단계» 추가 (정관 §3 «작업이 끝나면» 조항 옆 — 구현 시 한 줄).**
1. 이 세션에서 생긴 교정을 열거한다(«없음» 도 적는다).
2. 각 건을 위 표로 분류하고 **기존 조문 대조** 결과(있음/없음/부분)를 적는다.
3. R1·R6 은 그 자리에서 처리(값·코드), R3·R4·R5 는 PR, R7 은 learnings 후보, R2 는 기록 — **메모리에는 «어디에 등재했는가» 만 남긴다.** 메모리가 정본이 되는 순간 25건이 또 쌓인다.
4. `claim.ps1 -Release`.

## 2. `docs/learnings.md` 설계

**왜 필요한가.** 정관은 «규칙» 이고 SKILL 은 «기법» 인데, 「검사기가 CSS 값을 수치로 읽었다」 같은 것은 둘 다 아니다 — **일하는 방식의 함정**이다. 지금은 세션 보고와 메모리에 흩어져 다음 세션이 같은 함정에 빠진다(히어독 3회 헛돎이 그 증거 — 8/23 에 이미 한 번 겪은 뒤 8/25 에 또 3회).

**형식 — 한 건 = 3줄, 그 이상 쓰지 않는다.**
```
### L-NNN 교훈 한 줄 (명령형)
- 근거: <실측 1줄 — 날짜·건수·값>
- 등재: YYYY-MM-DD · 승인: JJ · 출처: <세션/PR/검증로그 §>
```
- **교훈은 «하지 마라/해라» 한 줄**이다. 왜는 근거 줄이 맡는다. 두 줄을 넘기면 그것은 조문 후보(R3/R4)이지 교훈이 아니다.
- **정관·SKILL 로 승격되면 이 파일에서 지우지 않고 «→ 정관 §N (승격 YYYY-MM-DD)» 를 붙인다.** 지우면 «왜 그렇게 했는지» 가 사라진다(`infra-backlog` 규칙 3 과 같다).
- 파일 상한 **100건**. 넘으면 오래된 것부터 «승격 또는 폐기» 를 판정한다 — 무한히 쌓이는 파일은 아무도 읽지 않는다.

**JJ 승인 경로.** 세션이 `## 후보` 절에 적는다 → JJ 가 읽고 `## 등재` 로 옮기는 PR 을 승인(또는 세션이 PR 로 올리고 JJ 가 지목 승인) → 머지. 후보 절에 **7일 넘게 머문 것은 자동 폐기 대상**으로 보고한다(ops-auditor 점검 항목 후보 — 구현 승인 대상).

**회수 목록 — 현재 9건** (L-001~L-005 는 첫 조문 세션 실측, L-006 이후는 그 뒤 회차에서 더해진 것).

## 3. 전파 경로 — 조문이 바뀌면 누가 영향을 받나

**문제.** #72 가 §4 «STATUS 의 뜻» 을 신설했는데 그것이 걸리는 에이전트는 셋(ops-auditor·content-scout·job-scout)이고, 정의 파일은 ops-auditor 하나만 참조를 갱신했다. 조문은 바뀌었는데 **누가 다시 읽어야 하는지가 PR 에 없다.**

**설계.**
1. **PR 본문에 «영향 에이전트» 란을 둔다** — 정본(CLAUDE.md·SKILL·스키마·게이트) 변경 PR 은 `영향: ops-auditor · content-scout · (없음)` 한 줄이 없으면 머지 조건 미달로 본다(정관 §0 머지 4조건에 5번째로 붙이는 안 — 구현 승인 대상). 세션이 채우고 JJ 가 승인 시 확인한다.
2. **에이전트 정의는 정관을 «절 번호»로 참조한다.** 정의 안에 조문을 베끼지 않는다(두 곳에 두면 한쪽이 뒤처진다 — content-scout 241행 사고). 형식: `정관 §4 «STATUS 의 뜻»` 처럼 **절 + 조항 이름**.
3. **전수 점검 (2026-08-26 실측)** — 에이전트 정의 3종의 정관 참조 8건 전부 유효한 절을 가리킨다: ops-auditor `§0`·`4절`·`5절`·`§4 «STATUS 의 뜻»` / job-scout `5절` / content-scout `5절`·`§0 «정본은 실물»`·`2절`. 깨진 참조 0건. 다만 **content-scout·job-scout 는 §4 «STATUS 의 뜻» 참조가 없다** — 조항은 «전 스케줄 작업 공통» 인데 두 정의가 그것을 모른다. 구현 시 두 정의의 리포트 규칙에 참조 한 줄 추가(영향 에이전트 란의 첫 적용 사례).
4. **정의 변경은 새 세션에서 검증한다** — 정관 §4 «언제 재는지» 조항 그대로.

## 4. 워커 신설 양식

**6질문 — 하나라도 답이 비면 워커를 만들지 않는다.**
1. **의존 소스**: 무엇을 읽는가(파일·API·정본). 읽는 것이 정본인가 사본인가.
2. **충돌 승자**: 같은 자리를 다른 워커·사람이 쓰면 누가 이기나(정본 쓰기는 스키마·게이트 경유만).
3. **필요 컨텍스트**: 판단에 꼭 필요한 정본·규격은 무엇인가(절 번호로).
4. **금지 컨텍스트**: 읽으면 안 되는 것(메모리·타 편 산출물·시크릿) — «메모리 off» 가 여기 들어간다.
5. **반복 교정**: 이 워커의 산출물에 사람이 같은 교정을 반복하면 어디로 가나(§1 라우팅 표 R-번호).
6. **교정 → 규칙**: 교정이 3회 반복되면 규칙으로 승격할 자리가 있나(없으면 그 워커는 배우지 못하는 워커다).

**템플릿 (`docs/workers/<이름>.md` 1장)**
```
# <워커 이름> — 양식 4 · 층: 감시/제안/해석 · 상태: 설계/시범/가동/보류
JOB            한 줄. «무엇을 만들어 누구에게 주는가»
TRIGGER        시각·이벤트·사람 호출 중 하나. 스케줄이면 정관 §4 규약
INPUTS         의존 소스 (정본/사본 표기) — 6질문 ①
PROCESS        단계 목록. 각 단계의 도구·산출물. 절차가 이미 정본에 있으면 절 참조만
OUTPUT         산출물 경로·형식. 정본 쓰기는 스키마·게이트 경유만(경유 파일명)
RULES          금지 자리: 게이트 판정 · 조문 · 발행 · 정본 직접 쓰기 — 워커마다 명문화
GATE           산출물이 통과해야 하는 검사(파일명 + 항목). 역검증 케이스 1건
성공지표       숫자 하나 + 측정 방법 + 판정 시점
FAIL CONDITION 무엇이면 STATUS: FAIL 인가(정관 §4 «STATUS 의 뜻» — 완수 여부)
6질문 답        ①~⑥ 한 줄씩
하네스 판정     봇 메모리 = 자산/부채 (아래)
```

## 5-1. Threads 발행 워커 — 양식 2호 · 층 **발행(신설)** (요약 · 전문은 `docs/workers/publish-threads.md`)

- **상태 설계 초안 — 구현 0줄 · 자격 미취득 · 발행 실적 0건.** «연다 ≠ 지금 발행한다»(정관 §0).
- **왜 새 층인가**: 감시·제안·해석은 산출물이 `reports\` 에서 끝나 실패 비용이 2점이다. 발행은 **바깥으로 나가고** 되돌림 비용이 0이 아니다 — 같은 층에 두면 채점이 거짓이 된다(이 워커 실패 비용 **0점**, 총 6/10).
- **트리거는 사람 호출이 아니라 파일**: `publish_approval\<ep>.json`(JJ 서명 · 본문 해시 · 체인 순서). 채팅 문장은 «어느 판본»인지 나중에 증명이 안 된다(§0 머지 조건 2와 같은 뿌리).
- **발행 직전 3확인** — 본문 해시 일치 / 승인 파일이 에이전트 손으로 안 만들어졌을 것 / 대상 편 일치. 하나라도 어긋나면 **거부**. 역검증 4건은 서로 분리하고 **정상 통과 케이스를 반드시 포함**한다.
- 🔴 **승인 파일 자기 서명·위조는 §6 금지 자리.** 열면 3확인이 «자기에게 내주는 허가»가 된다.
- **고정 댓글은 워커 밖 · 사람 자리** — 고정 여부를 API 로 되읽을 수 없어 성공 확인이 불가능하다.

## 6. 헤르메스 7자리 — 개요 · 공통 규칙 · 전개

> **Windows 실측 🟢 확정 (2026-08-26, JJ).** 헤르메스 = 외부 에이전트 런타임(Desktop + CLI). ① Desktop **v0.20.5 Bot Mode** 실물 확인 ② CLI 문법 — **`-q`(원샷) / `-Q`(프로그램)** ③ 프로필 경로 **`%LOCALAPPDATA%\hermes\profiles\<봇>`**(현재 `gumsu` 1개 실재). 메모리 off 는 프로필 단위 설정이며 실측 ③에서 확인됐다 — 따라서 감시층 ①은 착수 조건을 갖췄다(전개 0단계 통과).
>
> **해제 이력 (2026-08-26)** — `cua-driver-serve` 로그온 autostart 작업 해제: `cua-driver autostart disable` 은 비권한 `schtasks /Delete` 액세스 거부로 실패 → UAC 승격 `schtasks /Delete /TN cua-driver-serve /F` 성공 → `Get-ScheduledTask` 재조회 **not found**(실값 소멸 확인). 실측 보고서 파일이 레포에 없어 이력은 여기에 둔다.
>
> **프로바이더 조건 — `opencode-free` (2026-08-26 등재).** 시범은 무료 프로바이더로 돌리되 **무료 지속성은 보증되지 않는다**(약관 부재 · nemotron 무료 한시 전례). 그래서 7자리 전부의 FAIL CONDITION 에 「**프로바이더 실패·변경 시 조용한 전환 금지 — 중단·보고**」를 둔다(정관 §0 «조용히 실패하는 코드»: 다른 모델로 몰래 넘어가면 «크로스 모델» 이라는 전제 자체가 무너지는데 아무도 모른다). **플랜 B: Ollama 로컬** — 전환은 JJ 결정(R2)이고 봇이 하지 않는다.
>
> **공통 원칙 (2026-08-26 승격) — 헤르메스 봇 입력은 «공개 예정 텍스트»만.** 정관·`_facts.py`·검증로그·미발행 내부 문서(SKILL 원문 포함)는 투입하지 않는다. 근거: 무료 프로바이더는 요청이 *anonymously served* 되어 입력의 행방을 우리가 통제할 수 없다. 규격이 필요하면 **공개 가능한 검수 체크리스트**(`docs/workers/checklists/`, JJ 승인·20줄 이내·조문 원문 아님)로 바꿔 넘긴다. 각 시트의 INPUTS 는 이 원칙으로 다시 썼다.
>
> **gumsu 실증 (2026-08-26) — 비교 방향 반전 검출.** 시범 봇 `gumsu` 가 «수치는 동일한데 비교의 의미가 반전된» 문장을 잡았다 — guard 3(`assert_kit_facts`)은 수치 집합만 대조하므로 **A>B 가 B>A 로 뒤집혀도 통과한다**(guard 3 사각). 이것이 크로스 모델 검수가 게이트를 대체하지 못하되 **게이트가 못 보는 축**을 본다는 첫 실증이다. 사흘 시범 관찰 항목: **«guard 3 통과 ∧ 헤르메스 🔴» 케이스 수집** — 이 교집합의 건수·유형이 ①의 존재 이유를 숫자로 답한다(0건이면 ①을 접는다).
